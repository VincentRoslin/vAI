# Phase 18.5 — Deploy & Diagnostics (pulled forward from Phase 37)

> **Status: FINALIZED AT PHASE ENTRY** (2026-09-06). Owner-requested insertion:
> a way to run the **real** (release) build with the real settings for hands-on
> live-testing, with **local** probes the agent can read afterward. Not a course
> change — additive tooling. The log-file sink + diagnostics bundle were already
> earmarked for **Phase 37** (`docs/decisions/README.md`); this pulls them
> forward because live-testing needs them now. Phase 37 still owns the
> *installer* and clean-machine layout.

> **Architecture frozen at Phase 5.** Governing: **ADR-0015** (no telemetry — the
> probe is a file the owner chooses to share, never a beacon), `SECURITY.md` (no
> secrets / no conversation content in logs), `docs/spec/PERFORMANCE.md` (cheap on
> the hot path). **No new ADR** — implements the frozen "structured logging + a
> Phase 37 diagnostics bundle" policy.

## Objective
1. **A local deploy path** — `scripts/deploy-local.mjs` builds the release binary
   with the real config and launches it in place (no vite dev server, no
   installer). Prints the build id, exe path, and log path.
2. **A persistent file log sink** — rotating JSON-lines under
   `<app_data>/logs/`, redacted by the existing `RedactWriter`, size/age-swept.
   So a session the agent did not watch is still fully inspectable.
3. **A diagnostics snapshot** — `diag_export` writes one JSON file
   (`<app_data>/diagnostics/diag-<ts>.json`): build info, effective config
   (redacted), registry rows, resource snapshot, lifecycle statuses, the recent
   log lines, and host facts (`nvidia-smi`, OS). A Settings button triggers it.
4. **Debug-level UI breadcrumbs** — the frontend logs key actions (model load,
   send, voice start/stop, errors) through the existing `frontend_log` bridge so
   the agent can reconstruct what the owner did.

## Depends on
Phase 10 (logging — `RedactWriter`, ring buffer, reloadable level), Phase 8
(config — `<app_data>` resolution), Phase 11–17 (registry / resources /
lifecycle / conversation — the snapshot reads their state).

## Not in this phase
- **The Windows installer / MSI / sibling layout / first-run acquisition** —
  Phase 37. This phase's "deploy" is a local release run, not a distributable.
- **Code signing** — Phase 37.
- **A zipped/portable bundle** — the snapshot is a single JSON file; the agent
  reads it (or the log dir) directly off the machine. A portable archive is a
  Phase 37 concern (testing on another box).
- **Remote / cloud anything** — forbidden (ADR-0015).
- **Config-driven retention tuning** — fixed defaults (keep 7 files, cap ~50 MB);
  a `logging.*` key is a later addition if needed.

## Architecture notes
- **Ownership (Article I):** Rust owns the log files and the snapshot file
  (filesystem). The frontend only *triggers* an export and *displays* the
  returned path. The snapshot command reads already-owned in-process state +
  runs read-only host commands (`nvidia-smi`, `ver`).
- **The file sink is added after `logging::init()`** — `init()` runs before
  config is loaded, so the log dir is unknown then. `RedactWriter::drop` gains a
  second, optional destination behind a `OnceLock<NonBlocking>` that
  `enable_file_sink(dir)` fills once `setup()` has the path. Until then, only
  stdout + the ring buffer (unchanged).
- **Redaction is unchanged** — the file sink reuses the exact `RedactWriter`
  path, so the same secret shapes are scrubbed before a byte hits disk.
- **The snapshot is redacted twice:** the log lines are already redacted; the
  effective `AppConfig` is re-serialized through `logging::redact_line` before it
  goes in (defence in depth — config holds no secret today, but the guard stays).
- **No conversation content** in the snapshot — conversation *metadata* only
  (id, kind, message counts, timestamps), matching `SECURITY.md`.
- **`build.rs`** gains a git-SHA capture (`cargo:rustc-env=LOCALAI_GIT_SHA`),
  best-effort — empty string when git is unavailable.

## Steps

**18.5.1 — file log sink**
    Do:     `logging::enable_file_sink(dir: &Path) -> AppResult<PathBuf>` —
            `tracing_appender::rolling::daily(dir, "localai.jsonl")` behind a
            non-blocking lossy writer + its own `WorkerGuard`; `RedactWriter::
            drop` also writes the redacted line to it when set; a startup
            `sweep_logs(dir)` keeps the newest 7 `localai.jsonl*` and drops
            oldest while the dir exceeds ~50 MB. Wire it in `lib.rs::setup()`
            right after config loads (`<app_data>/logs`).
    Verify: `cargo test logging::` — a temp-dir sink writes a redacted line to
            the file; `sweep_logs` prunes a dir seeded with 10 dated files to 7.
            `tauri dev` → `<app_data>/logs/localai.jsonl.<date>` exists and grows.

**18.5.2 — `build.rs` git SHA**
    Do:     `src-tauri/build.rs` runs `git rev-parse --short HEAD` (best effort)
            → `cargo:rustc-env=LOCALAI_GIT_SHA`; also `cargo:rerun-if-changed`
            on `.git/HEAD`.
    Verify: `cargo build` then a test asserts `env!("LOCALAI_GIT_SHA")` is
            present (may be empty in a non-git checkout — the test allows that).

**18.5.3 — `diag` snapshot + IPC**
    Do:     `contracts` (or a small `diag` module): `DiagSnapshot { build,
            config, models, resources, lifecycle, recent_logs, host }`.
            `diag_snapshot() -> DiagSnapshot` (in-memory) and
            `diag_export() -> String` (writes `<app_data>/diagnostics/
            diag-<rfc3339>.json`, returns the path). Host facts: `nvidia-smi
            --query-gpu=... --format=csv` + OS string, both optional / read-only.
            Config + logs redacted.
    Verify: `cargo test` — `diag_snapshot` populates every field from a wired
            test app; `diag_export` writes a parseable file; a seeded secret in
            a fake log line does not appear in the snapshot.

**18.5.4 — Settings page + wrappers**
    Do:     `src/lib/ipc.ts`: `diagExport()`, `diagSnapshot()`. `Settings.tsx`:
            render the effective config read-only + an **Export diagnostics**
            button → calls `diagExport()` → shows the path + a "copy path"
            affordance. `contracts.ts` re-export `DiagSnapshot`. `setup.ts` mock.
    Verify: `node scripts/check.mjs`; `Settings.test.tsx` — the button calls
            `diag_export` and renders the returned path; `git diff --exit-code
            src/bindings`.

**18.5.5 — UI breadcrumbs**
    Do:     `ChatVoice.tsx` (+ `Models.tsx`): `log.info('ui', …)` on model
            load/unload, send, voice start/stop/transcript, and on every caught
            error (kind only, no content). Keep it to ~8 call sites.
    Verify: `tauri dev` → perform each action → the lines appear in
            `<app_data>/logs/…` with `target":"frontend"`.

**18.5.6 — `deploy-local.mjs`**
    Do:     `scripts/deploy-local.mjs`: `npm run build` → `cargo build --release
            --manifest-path src-tauri/Cargo.toml` → launch
            `src-tauri/target/release/localai.exe` (detached) → print
            `{ git_sha, exe, config: <app_data>/config.json, logs:
            <app_data>/logs, diagnostics: <app_data>/diagnostics }`.
            A `--no-launch` flag just builds + prints.
    Verify: `node scripts/deploy-local.mjs --no-launch` builds and prints the
            paths; a manual full run launches the window and the log file fills.

**18.5.7 — docs + gate + commit**
    Do:     `docs/verification/18_phase18.5_deploy-diagnostics.md`;
            `docs/spec/DEVELOPMENT.md` (§ the deploy loop + where logs/diagnostics

## Verification gate (physically executed)
1. `deploy-local.mjs` builds the release binary and launches it against the real
   `%APPDATA%` config; it prints the build SHA + log + diagnostics paths. *(18.5.6)*
2. A running session writes a **redacted** rotating JSON-lines log to
   `<app_data>/logs/`; a planted `Bearer …` / `"token":"…"` never reaches disk.
   *(18.5.1)*
3. Log rotation + sweep works — the dir does not grow without bound. *(18.5.1)*
4. `diag_export` produces one JSON file with build / config / registry /
   resources / lifecycle / recent logs / host facts — config + logs redacted, **no
   conversation content**. *(18.5.3, 18.5.4)*
5. The Settings **Export diagnostics** button writes the file and shows its path.
   *(18.5.4)*
6. UI actions (model load, send, voice) leave `target:"frontend"` breadcrumbs in
   the log. *(18.5.5)*
7. Full check suite green; bindings regenerated. *(18.5.7)*
